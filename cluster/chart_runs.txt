# Chart-family training runs: networks that are NOT IKFlow flows (branch chart-cvae).
# One line per run: <family> <robot> <run_name> <trainer args...>
#
# A SIBLING of ladder_runs.txt, not rows in it, on purpose. ladder_runs.txt is read by
# submit_ladder.sh --next and chain_ladder.sh, which submit every row as a 4-node IKFlow DDP
# rung through submit_train.sh; a cVAE row there would be picked up as "the next untrained
# flow rung" and launched with the flow trainer. The family column is what lets the next
# family (LOInK, ...) join this file without touching either. gen_manifest.py's
# _ladder_paths_match_export reads both files, so every run here must be benchmarked by a
# stage and every chart a stage names must be exported by a row here.
#
# Submitted by cluster/submit_chart_train.sh (one single-GPU job per run, NOT --exclusive,
# so two runs share a volta node); --all submits every row of this file. The run name is
# <robot>_<label>, and the in-job export writes models/<robot>/<robot>__<label>__step620000.pkl
# -- the path stage CVAE's items name (CVAE_RUNGS in gen_manifest.py).
#
# The cVAE (src/charts/cvae.py): encoder E(q, c) -> N(mu, sigma), decoder D(c, z) -> q, ELBO,
# 6 x 512 SiLU, one config, no sweep. Two latent rungs per robot, both PRE-REGISTERED and both
# benchmarked, final checkpoint (there is no chart selection to make):
#   * K = the flow's width (Panda 7, iiwa 8, screw 7, soft PCS 12), so the program's
#     decision-variable count is the record's and only the network differs;
#   * K = the redundancy, DOF - 6 (Panda 1, iiwa 1, screw 1, soft PCS 6), the latent the
#     self-motion actually needs.
# Recipe matched to the flow rungs (AdamW, lr 1.5e-4, StepLR 0.9795 every 2441 steps, 620000
# steps, batch 4096 on one GPU = the flows' 8 x 512 global batch, seed 0, the same datasets);
# those are the trainer's defaults, so only the latent width travels here.
#
# THE SCREW DATASET MUST BE REBUILT FIRST (cluster/CVAE_RUNBOOK.md): the original was deleted
# with ~/learned-ik-helix on 2026-10-02, and a rebuild is a NEW dataset, so the screw cVAEs are
# trained on different samples than the screw flow chart they are compared against.
# (Superseded 2026-10-19: the rebuild was proved bit-identical -- `screw7_p050_n6r` retrained on it
# equals `n6` tensor for tensor -- so the rebuilt screw dataset IS the flow's data.)

# ---------------------------------------------------------------------------------- LOInK --
# The LOInK chart (branch chart-loink, Thomas 2026-10-22; src/charts/loink.py): a bi-Lipschitz
# network G(q) = [y_hat; z] (BiLipNet, mu = 0.1), inverted by Davis-Yin splitting + a Newton
# polish, with an optional cost head J_hat(z, y_hat) = |z|^2_M + b(y_hat) that makes z = 0 the
# cost minimiser on each IK fibre. The latent width is FORCED, K = DOF - 6 (Panda / iiwa / screw 1,
# soft PCS 6), so no width travels here. Twelve pre-registered charts per robot, final checkpoint,
# no selection. The run name is <robot>_loink<cost><act><recipe>:
#   cost    m = matched: the program's own reported cost, 0.5 |q - q_nominal|^2 (soft PCS 0.5 |strain|^2);
#           x = mismatched: LOInK's eq. 18 joint-limit log-barrier on joints normalised to [-1, 1];
#           u = unstructured: no cost head (lambda = 0), the bi-Lipschitz chart alone;
#   act     r = relu (as published), t = tanh (smooth);
#   recipe  P = the project recipe: AdamW 1.5e-4, StepLR 0.9795 / 2441, 620000 steps, batch 4096
#               (the flows' and cVAE's);
#           A = the paper's: Adam 1e-3, reduce-on-plateau, 150000 steps (~3 epochs), batch 500.
# Every row carries its recipe's --batch_size / --max_steps EXPLICITLY: train_chart.sh appends its
# own --batch_size / --max_steps before the row's args (the trainer's argparse takes the last
# occurrence) and reads MAX_STEPS / BATCH / FINAL_STEP from the row, so an A row trains 150000 steps
# at batch 500 and exports models/<robot>/<robot>__loink<c><a>A__step150000.pkl; a P row exports
# ...__step620000.pkl. Those are the paths stages LOINK* name (LOINK_RUNGS in gen_manifest.py).
# Same datasets as the flow charts on every robot (the screw dataset: the bit-identical rebuild).
#
# ORDER, and what --pair makes of it: robot-major, then cost (m, x, u), activation (r, t), recipe
# (P, A). Consecutive rows therefore pair a chart's P and A recipes on one node -- one robot, one
# cost, one activation -- which is valid but leaves the A run's GPU idle for most of the P run's
# wall. The runbook (cluster/LOINK_RUNBOOK.md) submits the recipes separately instead; consecutive
# MATCHING rows then pair relu with tanh at one robot, cost and recipe:
#   ONLY='_loink[mxu][rt]P$' PAIRS=1 bash cluster/submit_chart_train.sh --all <P walltime>   # 24 rows, 12 jobs
#   ONLY='_loink[mxu][rt]A$' PAIRS=1 bash cluster/submit_chart_train.sh --all <A walltime>   # 24 rows, 12 jobs
