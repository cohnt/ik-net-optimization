# The reduced-capacity chart ladder. One line per training run, in submission order.
# Fields: <robot> <run_name> <architecture args...>
#
# Read this next to the hypothesis it tests. FrEIA's GLOW blocks soft-clamp the log-scale
# to clamp*0.636*atan(s/clamp), so the flow's worst-case output gain over nb_nodes blocks
# is about exp(2.4975 * nb_nodes) at rnvp_clamp=2.5:
#
#     nb_nodes    12        8        6        4
#     ceiling     1.0e13    4.8e08   3.2e06   2.2e04
#
# and the runaway configurations that cost the learned arm its cells sit at 1e7-1e16 rad.
# So DEPTH lowers the ceiling. WIDTH (coeff_fn_internal_size) lowers accuracy while leaving
# the ceiling untouched -- which is why the w256 arms are here: they are the control that
# separates "less accurate" from "less headroom". Without them a win could not be attributed.
#
# Held fixed across the whole ladder, deliberately:
#   * dim_latent_space at each robot's own baseline (iiwa14: 8, panda: 7). The latent width
#     IS the program's decision-variable count, so varying it would change the optimization
#     problem rather than the chart. Verified: 21 vars for iiwa, 20 for panda, at every rung.
#   * rnvp_clamp = 2.5, confirmed optimal for these weights by the sweep in CLAUDE.md.
#   * 620k steps, batch 512/rank, lr 1.5e-4, step_lr_every 2441 -- ddp_r1's actual values,
#     so architecture is the only variable.
#
# Order: iiwa first (it has the live deficit), n6 first within it (elated-firefly-11 is a
# 6-block chart, so the Phase 0 pilot gives that rung a sanity reference), then n4 for the
# lowest ceiling, then the rest. panda_n12 leads the Panda block because it is the
# self-trained control every other Panda rung is compared against -- without it, a reduced
# Panda chart is confounded with "our recipe vs the upstream pretrained one".
#
# iiwa14's 12x1024 rung is NOT here: it already exists as iiwa14_ddp_r1.

iiwa14  iiwa14_n6        --nb_nodes=6
iiwa14  iiwa14_n4        --nb_nodes=4
iiwa14  iiwa14_n8        --nb_nodes=8
iiwa14  iiwa14_n12_w256  --nb_nodes=12 --coeff_fn_internal_size=256
panda   panda_n12        --nb_nodes=12 --dim_latent_space=7
panda   panda_n6         --nb_nodes=6  --dim_latent_space=7
panda   panda_n4         --nb_nodes=4  --dim_latent_space=7
panda   panda_n8         --nb_nodes=8  --dim_latent_space=7
panda   panda_n12_w256   --nb_nodes=12 --dim_latent_space=7 --coeff_fn_internal_size=256

# The soft PCS (piecewise constant strain) arm. The fielded rung is PRE-REGISTERED at
# nb_nodes = 6 -- the most expressive the gain-ceiling rule admits below the ~1e7 runaway
# band -- and n4 and n8 are trained and reported as the ladder MEASUREMENT, with n8 above
# the ceiling as the control that the ceiling matters. Selecting whichever rung benchmarks
# best is disqualified.
# dim_latent_space is the rung's own DoF count and is not a free choice: InvertFlow writes
# ndof entries into a buffer of width network_width.
soft12  soft12_n6   --nb_nodes=6 --dim_latent_space=12
soft12  soft12_n4   --nb_nodes=4 --dim_latent_space=12
soft12  soft12_n8   --nb_nodes=8 --dim_latent_space=12
soft9   soft9_n6    --nb_nodes=6 --dim_latent_space=9
soft16  soft16_n6   --nb_nodes=6 --dim_latent_space=16

# ---------------------------------------------------------------------------------------
# The screw-joint arm. Its charts are 7-wide -- it is a 7-DoF arm -- so dim_latent_space
# is the Panda's baseline, and it is held fixed across the ladder for the same reason: the
# latent width IS the program's decision-variable count (20 variables here: 6 + 7 + 7), so
# varying it would change the optimization problem rather than the chart.
#
# THE FIELDED RUNG IS PRE-REGISTERED AT n6, before any cell is read. That is the Panda's
# adopted rung and this is a 7-DoF arm, so it is the obvious prior; n4 and n8 are trained
# and REPORTED as the ladder measurement, never selected from. Picking whichever benchmarks
# best is selecting on the test set.
#
# EACH PITCH IS A DIFFERENT ROBOT, so it needs its own 25M-sample dataset and its own 620k
# steps: it cannot borrow another rung's chart, because the arm's links are its own.
#
# screw7_p000 IS NOT TRAINED. At pitch 0 the arm is an ordinary S-R-S manipulator, and the
# project already fields two of those with analytic columns, so a chart for it would spend
# 620k steps rediscovering that an algebraic arm is algebraic. The spec and its dataset
# exist; the rung does not. Thomas, 2026-09-25: "Seems like a waste of time to train a
# model for screw7_p000. We already have analytic arms, we don't need a specific control
# example here." So the ladder is 5 training runs: three architectures on the primary rung,
# plus the two other pitches at the adopted architecture.
#
# BUILD THE DATASETS ONE AT A TIME: ikflow's end-of-run summary scans every dataset in the
# shared cache directory, so a concurrent sibling's half-written tensor makes a finished job
# exit 1 and withhold the .DONE sentinel that train_flow.sh hard-fails without.

screw7_p050  screw7_p050_n6   --nb_nodes=6 --dim_latent_space=7
screw7_p050  screw7_p050_n4   --nb_nodes=4 --dim_latent_space=7
screw7_p050  screw7_p050_n8   --nb_nodes=8 --dim_latent_space=7
screw7_p025  screw7_p025_n6   --nb_nodes=6 --dim_latent_space=7
screw7_p100  screw7_p100_n6   --nb_nodes=6 --dim_latent_space=7
